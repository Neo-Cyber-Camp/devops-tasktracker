# Jour 4 : déploiement continu et supervision

Objectif de la journée : chaque push sur `main` déploie automatiquement la nouvelle version sur votre machine de l'Atelier, et vous vérifiez que l'application vit dans Prometheus et Grafana.

## 1. Objectif et architecture

Hier, chaque commit poussé sur `main` produisait une image sur `ghcr.io`. Aujourd'hui, la chaîne va jusqu'au bout : un quatrième job, `deploy`, installe cette image sur une machine et vérifie qu'elle répond, puis Prometheus et Grafana montrent comment elle se porte.

Cette semaine, la machine de l'Atelier joue trois rôles à la fois :

| Rôle | Sur la machine de l'Atelier |
|---|---|
| Poste de développement | votre clone `~/devops-tasktracker`, où vous éditez, testez, commitez et poussez |
| Runner GitHub Actions | un service qui exécute le job `deploy` de votre fork, et lui seul |
| Production | la stack `nginx`, `app`, `db`, `prometheus` et `grafana`, lancée par le job `deploy` |

Le runner est un programme de GitHub installé sur la machine. C'est lui qui contacte GitHub, en HTTPS sortant, pour demander s'il y a un job à exécuter : GitHub n'ouvre jamais de connexion vers la machine. Il n'y a donc aucun port entrant à ouvrir et aucune clé SSH à confier à GitHub, et la machine peut rester derrière un pare-feu. Les jobs `lint`, `test` et `build` continuent de tourner sur les machines de GitHub ; seul `deploy` tourne sur votre runner.

Ce matin, dans le lab `superviser-service-prometheus-grafana`, vous avez vu Grafana dans Firefox. La machine de l'Atelier n'a pas de navigateur : ici, vous interrogez Prometheus et Grafana avec `curl`, sur leur API.

**Résultat attendu** : vous savez dire où tourne chacun des quatre jobs, et pourquoi le runner n'a besoin d'aucun port entrant.

## 3. Les métriques de l'application

Lisez `src/metrics.js` (`less src/metrics.js`, `q` pour quitter) :

| Élément | Ce qu'il mesure |
|---|---|
| `collectDefaultMetrics` | l'état du processus Node.js : mémoire, temps processeur, boucle d'événements |
| `http_requests_total` | un **compteur** : le nombre de requêtes traitées, par méthode, route et code de réponse ; il ne fait que monter, et repart de zéro quand l'application redémarre |
| `http_request_duration_seconds` | un **histogramme** : chaque durée est rangée dans une tranche (`buckets`, de 5 ms à 2,5 s), ce qui permet de calculer des percentiles |
| `metricsMiddleware` | à la fin de chaque réponse (`finish`), incrémente le compteur et enregistre la durée |

Dans `src/app.js`, `app.use(metricsMiddleware)` s'applique à toutes les requêtes, et la route `GET /metrics` renvoie les valeurs au format texte que lit Prometheus. Reconstruisez la stack avec ce code, puis faites quelques requêtes :

```bash
docker compose up -d --build --wait
curl -s localhost/tasks > /dev/null
curl -s -o /dev/null -X DELETE localhost/tasks/12345
curl -s localhost/metrics | grep '^http_requests_total'
```

Pourquoi l'étiquette `route` contient le motif Express (`/tasks/:id`) et jamais l'URL reçue (`/tasks/12345`) : Prometheus crée une **série temporelle** pour chaque combinaison de valeurs d'étiquettes. Avec l'URL brute, chaque identifiant de tâche créerait une nouvelle série, et quelques milliers de tâches suffiraient à saturer la mémoire de Prometheus. Avec le motif, le nombre de séries reste fixe. Pour la même raison, une URL qui ne correspond à aucune route (un robot qui essaie des adresses au hasard) est comptée sous `route="non_route"`.

En production, `/metrics` ne passe pas par le reverse proxy public : Prometheus le lit directement sur `app:3000`, par le réseau interne de Compose. Ici, le passage par Nginx sert seulement à le regarder avec `curl`.

**Résultat attendu** : parmi les lignes affichées, `http_requests_total{method="GET",route="/tasks",status_code="200"}` et `http_requests_total{method="DELETE",route="/tasks/:id",status_code="404"}`, avec le motif `/tasks/:id` et non `/tasks/12345`.

## 4. La supervision dans Compose

Avant de toucher à `compose.yml`, arrêtez la stack actuelle : vous allez changer le nom du projet Compose, et Compose ne retrouverait plus ces conteneurs sous le nouveau nom (ils garderaient le port 80).

```bash
docker compose down
nano compose.yml
```

Ajoutez en **première ligne** du fichier, sans indentation :

```yaml
name: tasktracker
```

Sans cette ligne, Compose nomme le projet d'après le dossier. Or, dès la section 8, c'est le runner qui lance la stack, depuis sa propre copie de votre fork (`/opt/actions-runner/_work/devops-tasktracker/devops-tasktracker`). Avec un nom fixe, votre clone et la copie du runner pilotent le **même** projet, donc les mêmes conteneurs, au lieu de deux stacks qui se disputeraient les ports 80, 9090 et 3000.

Ajoutez ensuite deux services, qui respectent ces exigences :

| Exigence | `prometheus` | `grafana` |
|---|---|---|
| Image | `prom/prometheus:v3.13.3` | `grafana/grafana:13.2.2` |
| Port publié sur l'hôte | `9090:9090` | `3000:3000` |
| Montages | `./monitoring/prometheus:/etc/prometheus:ro` (le dossier entier : `prometheus.yml` et `alerts.yml`) et le volume nommé `prometheus-data:/prometheus` | `./monitoring/grafana/provisioning:/etc/grafana/provisioning:ro` et `./monitoring/grafana/dashboards:/etc/grafana/dashboards:ro`, **aucun volume de données** |
| Environnement | aucun | `GF_SECURITY_ADMIN_PASSWORD: ${GRAFANA_ADMIN_PASSWORD:-admin}` |
| Démarre après | `app` (`depends_on`) | `prometheus` (`depends_on`) |

Déclarez aussi `prometheus-data:` sous le bloc `volumes:` de premier niveau, à côté de `db-data:`.

Pourquoi ces choix :

- **Des dossiers montés, pas des fichiers seuls.** Quand Git remplace un fichier (checkout, pull), un conteneur qui monte ce fichier seul continue de voir l'ancienne version ; avec un dossier monté, il voit la nouvelle.
- **Grafana sans volume de données.** Tout ce que Grafana doit connaître vient du dépôt : la source de données et le tableau de bord sont chargés depuis `monitoring/grafana/` à chaque démarrage (c'est le *provisioning*). À chaque recréation du conteneur, Grafana repart de zéro et réapplique le mot de passe de `GF_SECURITY_ADMIN_PASSWORD`. Ce qui n'est pas dans le dépôt disparaît : c'est voulu, un tableau de bord se versionne comme du code.
- **`${GRAFANA_ADMIN_PASSWORD:-admin}`.** Compose prend la variable `GRAFANA_ADMIN_PASSWORD` si elle est définie et non vide, `admin` sinon. La section 10 la fournit depuis un secret GitHub.
- **Des ports publiés pour Prometheus et Grafana** : vous les interrogez avec `curl` depuis la machine. `app` et `db` restent sans port publié, derrière Nginx.

Lancez la stack complète et vérifiez chaque service :

```bash
docker compose up -d --build --wait
docker compose ps
curl -s localhost:9090/api/v1/targets | python3 -m json.tool | grep -E '"job"|"health"'
curl -s -u admin:admin localhost:3000/api/health
curl -s -u admin:admin localhost:3000/api/datasources/uid/prometheus/health
```

Grafana met une trentaine de secondes à démarrer la première fois, et Prometheus lit l'application toutes les 15 secondes : si une commande ne répond pas encore, ou si la cible affiche `"health": "unknown"`, attendez un peu et relancez-la.

Si `docker compose up` répond `port is already allocated` pour le port 3000, un `npm start` tourne encore dans une autre console : arrêtez-le avec `Ctrl+C`. Pour le port 80, `docker ps` montre le conteneur qui l'occupe.

Enregistrez et poussez :

```bash
git add compose.yml
git commit -m "feat: Prometheus et Grafana dans la stack"
git push
```

**Résultat attendu** : `docker compose ps` montre cinq services en marche ; la cible `"job": "app"` est `"health": "up"` ; `/api/health` de Grafana répond `"database": "ok"` ; la source de données répond `"status": "OK"`.

## 5. Le tableau de bord, versionné dans le dépôt

Le fichier `monitoring/grafana/dashboards/tasktracker.json` décrit le tableau de bord `Tasktracker` (uid `tasktracker`, à ne pas changer). Il contient un panneau, le débit de requêtes par route. Ajoutez-lui un second panneau, la latence au 95e percentile :

```json
    {
      "id": 2,
      "type": "timeseries",
      "title": "Latence p95 (secondes)",
      "datasource": { "type": "prometheus", "uid": "prometheus" },
      "gridPos": { "h": 8, "w": 12, "x": 12, "y": 0 },
      "targets": [
        {
          "refId": "A",
          "datasource": { "type": "prometheus", "uid": "prometheus" },
          "expr": "histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket[5m])))"
        }
      ]
    }
```

Les panneaux sont les éléments de la liste `"panels": [ ... ]`, séparés par des virgules. Trouvez la fin du premier panneau :

```bash
grep -n '"type": "timeseries"' monitoring/grafana/dashboards/tasktracker.json
nano +27 monitoring/grafana/dashboards/tasktracker.json
```

`grep` affiche la ligne 26, `"type": "timeseries"` ; la ligne 27, `    }`, ferme le premier panneau, juste avant la ligne `  ],` qui ferme la liste. Sur la ligne 27, ajoutez une virgule après l'accolade (`    },`), puis collez le bloc ci-dessus sur la ligne suivante (`Ctrl+Shift+V`), avant `  ],`. Enregistrez (`Ctrl+O`, `Entrée`) et quittez (`Ctrl+X`).

Vérifiez que le fichier est toujours du JSON valide, puis rechargez Grafana :

```bash
python3 -m json.tool monitoring/grafana/dashboards/tasktracker.json > /dev/null && echo "JSON valide"
docker compose restart grafana
sleep 10
curl -s -u admin:admin localhost:3000/api/dashboards/uid/tasktracker | python3 -c "import json, sys; d = json.load(sys.stdin)['dashboard']; print(len(d['panels']), [p['title'] for p in d['panels']])"
```

Si la dernière commande affiche une erreur Python, Grafana n'a pas fini de redémarrer : relancez-la quelques secondes plus tard. Un message comme `Expecting ',' delimiter: line 28 column 5` signale la virgule oubliée entre les deux panneaux : Grafana ignorerait tout le fichier. Corrigez le fichier dans `nano`, puis relancez ces quatre commandes.

Enregistrez et poussez :

```bash
git add monitoring/grafana/dashboards/tasktracker.json
git commit -m "feat: panneau de latence p95"
git push
```

Ici, vous modifiez le JSON directement, car la machine n'a pas de navigateur. Quand vous modifiez un tableau de bord dans le navigateur, comme ce matin, `./monitoring/export-dashboard.sh` le récupère depuis Grafana et réécrit ce fichier ; vous le commitez ensuite. Dans les deux cas, c'est le fichier du dépôt qui fait foi : un panneau ajouté seulement dans Grafana disparaît au prochain déploiement, et l'Atelier ne le compte pas.

**Résultat attendu** : la dernière commande affiche `2 ['Requetes par seconde', 'Latence p95 (secondes)']`, et le commit est poussé sur votre fork.

## 6. Protéger votre fork, avant le runner

Votre fork est public. N'importe qui peut le forker et vous proposer une pull request, et une pull request peut modifier le workflow lui-même : c'est son code, pas le vôtre, qui décide alors où tournent ses jobs. Dès que votre runner existe, une pull request pourrait donc faire exécuter son code sur la machine de l'Atelier, qui contient aussi votre accès à GitHub (la connexion créée par `atelier-init`).

Sur votre ordinateur, dans votre fork sur GitHub : **Settings**, **Actions**, **General**, rubrique **Approval for running fork pull request workflows from contributors**, choisissez **Require approval for all external contributors**, puis **Save**. Avec ce réglage, aucun workflow d'une pull request venant d'un fork ne démarre sans votre approbation. La valeur par défaut, `Require approval for first-time contributors`, laisse passer toute personne dont une contribution a déjà été acceptée.

Vérifiez depuis la console de l'Atelier :

```bash
GH_USER=$(gh api user --jq .login)
gh api "repos/$GH_USER/devops-tasktracker/actions/permissions/fork-pr-contributor-approval" --jq .approval_policy
```

Le playbook de la section 7 lit ce même réglage à chaque exécution, et refuse d'installer le runner tant qu'il ne vaut pas `all_external_contributors`.

Cette semaine, n'approuvez jamais une pull request venant d'un fork sur votre dépôt : son code tournerait sur cette machine.

**Résultat attendu** : la commande affiche `all_external_contributors`.

## 7. Installer le runner avec Ansible

Le rôle `deploy/roles/runner` installe le runner sur les machines du groupe `app` de l'inventaire. Aujourd'hui, ce groupe contient une seule machine : celle de l'Atelier elle-même.

Créez l'inventaire `deploy/inventaire.ini` (`nano deploy/inventaire.ini`) :

```ini
[app]
projet ansible_connection=local
```

`projet` est le nom qu'Ansible donne à la machine (le runner s'appellera `range-projet`) ; `ansible_connection=local` exécute les tâches sur la machine où vous lancez Ansible, sans SSH. Au projet final, la cible sera une autre machine, jointe par SSH : c'est l'inventaire qui changera.

Créez `deploy/group_vars/app.yml` sur le modèle de `app.yml.example`, avec votre identifiant GitHub, et vérifiez qu'Ansible lit la variable :

```bash
GH_USER=$(gh api user --jq .login)
printf 'github_owner: %s\n' "$GH_USER" > deploy/group_vars/app.yml
cat deploy/group_vars/app.yml
ansible -i deploy/inventaire.ini app -m ansible.builtin.debug -a var=github_owner
```

Lisez ensuite `deploy/roles/runner/tasks/main.yml`, tâche par tâche :

| Tâches | Ce qu'elles font |
|---|---|
| Lire le réglage d'approbation, Arrêter si GitHub n'a pas donné le réglage, Refuser d'enregistrer le runner | lisent le réglage de la section 6 avec votre connexion `gh`, sur le poste de contrôle (`delegate_to: localhost`, `become: false`), et arrêtent tout s'il ne vaut pas `all_external_contributors`. Elles passent **avant** toute installation : un refus ne modifie rien sur la machine |
| Installer les bibliothèques | les paquets dont le runner a besoin ; `cache_valid_time` évite de relancer `apt update` à chaque passage |
| Créer l'utilisateur du runner | l'utilisateur `runner`, qui n'est pas root, ajouté au groupe `docker` pour lancer la stack |
| Créer le dossier, Télécharger, Extraire | `/opt/actions-runner`, archive officielle vérifiée par sa somme de contrôle SHA-256, extraite une seule fois (`creates:`) |
| Savoir si le runner est déjà enregistré, Exiger le jeton | le jeton d'enregistrement n'est exigé qu'au premier passage |
| Enregistrer le runner | `config.sh` lancé en tant que `runner` : nom `range-projet`, étiquette `range`, `--replace` (un runner du même nom est remplacé, pas dupliqué). Le jeton passe par une variable d'environnement et `no_log: true` le cache : il n'apparaît ni dans la sortie d'Ansible ni dans la liste des processus |
| Installer le service systemd, Lire le nom du service, Démarrer | le runner devient un service, démarré maintenant et à chaque démarrage de la machine |

Le runner ne tourne pas en root, mais être membre du groupe `docker` revient à avoir les droits de root sur la machine : un job qui tourne sur ce runner peut tout faire sur la machine de l'Atelier, y compris lire votre connexion GitHub. C'est pourquoi le réglage de la section 6 passe avant, et pourquoi la section 8 ne laisse qu'un seul job atteindre le runner.

Lancez le playbook avec un jeton d'enregistrement. GitHub le fabrique à la demande, il n'est valable qu'une heure et ne sert qu'à enregistrer un runner : générez-le juste avant, dans la même commande.

```bash
RUNNER_TOKEN=$(gh api -X POST "repos/$GH_USER/devops-tasktracker/actions/runners/registration-token" --jq .token) \
  ansible-playbook -i deploy/inventaire.ini deploy/site.yml
```

Relancez-le ensuite sans jeton : le runner est déjà enregistré, rien ne doit changer.

```bash
ansible-playbook -i deploy/inventaire.ini deploy/site.yml
systemctl list-units 'actions.runner.*'
gh api "repos/$GH_USER/devops-tasktracker/actions/runners" --jq '.runners[] | .name + " " + .status'
```

Enregistrez et poussez l'inventaire et la variable (le jeton, lui, n'est écrit nulle part) :

```bash
git add deploy/inventaire.ini deploy/group_vars/app.yml
git commit -m "feat: inventaire du runner"
git push
```

Si le playbook s'arrête sur « Refuser d enregistrer le runner », le réglage de la section 6 n'est pas en place : corrigez-le, puis relancez la commande avec le jeton. S'il s'arrête sur « Arreter si GitHub n a pas donne le reglage », lisez le message : identifiant faux dans `deploy/group_vars/app.yml`, `gh` non connecté (relancez `atelier-init`), ou GitHub qui ne répond pas (relancez dans une minute).

**Résultat attendu** : la commande `ansible ... -m ansible.builtin.debug` affiche `"github_owner"` avec votre identifiant ; le récapitulatif `PLAY RECAP` du premier passage affiche `failed=0`, celui du second `changed=0` et `failed=0` ; `systemctl` montre un service `actions.runner.` en `active running` ; GitHub affiche `range-projet online`, et la page **Settings**, **Actions**, **Runners** de votre fork montre `range-projet` à l'état **Idle**.

## 8. Le job de déploiement

Ajoutez à `.github/workflows/ci.yml` un quatrième job, `deploy`, au même niveau que `build`. Le job complet n'est pas donné ; voici ce qu'il doit contenir.

| Clé | Valeur | Pourquoi |
|---|---|---|
| `needs` | `build` | on ne déploie que l'image construite et publiée par ce même run |
| `if` | exactement la ligne ci-dessous | le job ne part que sur un push vers `main` ou un lancement manuel, jamais sur une pull request |
| `runs-on` | `[self-hosted, range]` | les étiquettes de votre runner : ce job, et lui seul, tourne sur la machine de l'Atelier |
| `permissions` | `contents: read` et `packages: read` | lire le code et tirer l'image privée de `ghcr.io`, rien d'autre |
| `concurrency` | un `group:` fixe (par exemple `deploy-range`) et `cancel-in-progress: false` | deux déploiements ne tournent jamais en même temps sur la machine ; un déploiement commencé va jusqu'au bout, et parmi ceux qui arrivent entre-temps, seul le plus récent attend son tour |

```yaml
    if: github.ref == 'refs/heads/main' && (github.event_name == 'push' || github.event_name == 'workflow_dispatch')
```

Les étapes, dans l'ordre :

1. `actions/checkout@v7` : le runner a besoin de `compose.yml`, de `nginx/` et de `monitoring/` de ce commit.
2. `docker/login-action@v4` vers `ghcr.io`, avec `username: ${{ github.actor }}` et `password: ${{ secrets.GITHUB_TOKEN }}`, comme dans le job `build` (sans son `if:`).
3. Une étape `run:` qui enchaîne ces quatre commandes :

| Commande | Rôle |
|---|---|
| `export APP_IMAGE="ghcr.io/${GITHUB_REPOSITORY,,}:sha-${GITHUB_SHA}"` | l'image exacte de ce commit, celle que `build` vient de publier ; `${GITHUB_REPOSITORY,,}` met le nom du dépôt en minuscules, obligatoire sur `ghcr.io` |
| `docker compose pull app` | télécharge cette image depuis `ghcr.io` |
| `docker compose up -d --no-build --force-recreate --remove-orphans --wait --wait-timeout 180` | recrée les conteneurs avec l'image téléchargée (`--no-build` : on ne reconstruit jamais sur la machine de production) et attend qu'ils soient en bonne santé |
| `curl -fsS --retry 10 --retry-delay 3 --retry-all-errors http://localhost/health` | le job n'est vert que si l'application répond via Nginx |

Trois règles, que l'Atelier vérifie :

- **Aucun autre job sur le runner.** `lint`, `test` et `build` restent sur `ubuntu-latest` ; seul `deploy` porte `self-hosted` ou `range`.
- **Le `if` exact.** Sans lui, le job partirait aussi sur les pull requests, avec le code de la pull request.
- **Pas d'autre déclencheur** que `push`, `pull_request` et `workflow_dispatch` dans ce workflow : un `schedule`, par exemple, lancerait le déploiement sur `main` sans aucun push. Et, comme au jour 3, jamais `pull_request_target`.

Poussez, puis suivez le run dans l'onglet **Actions** de votre fork, sur votre ordinateur : `lint` et `test`, puis `build`, puis `deploy`. Le job `deploy` affiche un instant `Waiting for a runner to pick up this job`, puis démarre ; l'étape **Set up job** de son journal indique `Runner name: 'range-projet'`. Une fois le job vert, vérifiez sur la machine que la version qui tourne est bien celle de votre dernier commit :

```bash
docker compose ps
curl -s localhost/health
git rev-parse HEAD
docker inspect --format '{{ index .Config.Labels "org.opencontainers.image.revision" }}' $(docker compose ps -q app)
```

Désormais, c'est le runner qui lance la stack, depuis sa copie de votre fork. Ne relancez plus `docker compose up --build` dans `~/devops-tasktracker` : vous remplaceriez l'image de `ghcr.io` par une image construite sur la machine. Pour changer quoi que ce soit (code, `compose.yml`, tableau de bord), commitez et poussez : le pipeline déploie.

> **Machine neuve.** Si vous rouvrez l'Atelier, la machine ne contient plus ni runner ni stack. Dans l'ordre : `atelier-init`, `cd ~/devops-tasktracker`, les commandes `GH_USER=...` puis `RUNNER_TOKEN=... ansible-playbook ...` de la section 7, avec un nouveau jeton (`--replace` garde un seul runner `range-projet`), puis `gh workflow run ci.yml --ref main`, qui relance le pipeline sans commit : le job `deploy` installe la stack sur la nouvelle machine. Le réglage de la section 6 est sur GitHub : il reste en place.

> **Runner hors ligne.** Un push fait pendant que le runner est hors ligne (lab terminé, par exemple) laisse le job `deploy` en attente, à l'état **Queued** : il démarre dès que le runner revient en ligne, et GitHub l'abandonne au bout de 24 heures.

**Résultat attendu** : les quatre jobs sont verts pour votre dernier commit, `deploy` a tourné sur `range-projet`, `docker compose ps` montre l'image `ghcr.io/<votre-compte>/devops-tasktracker:sha-...` pour `app`, et les deux dernières commandes affichent le même numéro de commit.

## 9. Observer

Générez un peu de trafic, puis demandez à Prometheus le débit par route :

```bash
for i in $(seq 1 30); do curl -s -o /dev/null localhost/tasks; done
sleep 20
curl -s localhost:9090/api/v1/query --data-urlencode 'query=sum by (route) (rate(http_requests_total[1m]))' | python3 -m json.tool
curl -s localhost:9090/api/v1/rules | python3 -m json.tool | grep -E '"name"|"state"'
```

`rate()` transforme le compteur, qui ne fait que monter, en requêtes par seconde ; il absorbe aussi la remise à zéro du compteur quand l'application redémarre. L'alerte `AppDown` est chargée, à l'état `inactive`.

Simulez maintenant une panne : arrêtez l'application et observez l'alerte.

```bash
docker compose stop app
for i in $(seq 1 24); do date +%T; curl -s localhost:9090/api/v1/alerts | python3 -m json.tool | grep -E '"alertname"|"state"'; sleep 5; done
```

La boucle affiche l'état de l'alerte toutes les 5 secondes pendant 2 minutes (`Ctrl+C` pour l'arrêter plus tôt). En 30 secondes au plus, Prometheus n'arrive plus à lire `app:3000` (`up{job="app"}` vaut 0) : l'alerte apparaît à l'état `pending`. Elle doit rester vraie pendant 1 minute (`for: 1m` dans `alerts.yml`) avant de passer à `firing` : ce délai évite d'alerter pour un simple redémarrage. Redémarrez ensuite l'application, et vérifiez que l'alerte disparaît :

```bash
docker compose start app
docker compose ps
curl -s localhost/health
sleep 40
curl -s localhost:9090/api/v1/alerts | python3 -m json.tool | grep -E '"alertname"|"state"'
```

Si `curl` répond `502 Bad Gateway` alors que `app` est en bonne santé, Nginx cherche encore l'ancienne adresse du conteneur : `docker compose restart nginx`, puis relancez le `curl`. `docker compose stop` et `start` agissent sur les conteneurs lancés par le runner, parce que votre clone et sa copie partagent le nom de projet `tasktracker`.

**Résultat attendu** : vous avez vu `AppDown` passer de `pending` à `firing` ; après le redémarrage, `curl -s localhost/health` répond `{"status":"ok"}` et la dernière commande n'affiche plus rien (l'alerte est résolue).

## 10. Secret optionnel : le mot de passe de Grafana

Le mot de passe `admin` de Grafana est écrit dans ce guide, donc connu de tous. Remplacez-le par un secret du dépôt :

1. Sur GitHub, dans votre fork : **Settings**, **Secrets and variables**, **Actions**, **New repository secret**. Nom : `GRAFANA_ADMIN_PASSWORD`, valeur : un mot de passe de votre choix.
2. Dans le job `deploy`, ajoutez à l'étape `run:` :

```yaml
        env:
          GRAFANA_ADMIN_PASSWORD: ${{ secrets.GRAFANA_ADMIN_PASSWORD }}
```

3. Poussez, et attendez la fin du job `deploy`. Grafana, recréé sans volume de données, applique le nouveau mot de passe.

Vérifiez, en tapant le mot de passe sans qu'il s'affiche ni reste dans l'historique de la console :

```bash
curl -s -o /dev/null -w '%{http_code}\n' -u admin:admin localhost:3000/api/dashboards/uid/tasktracker
read -rsp 'Mot de passe Grafana : ' GF_PASS; echo
curl -s -o /dev/null -w '%{http_code}\n' -u "admin:$GF_PASS" localhost:3000/api/dashboards/uid/tasktracker
```

GitHub masque la valeur du secret dans les journaux, et ne la donne jamais aux workflows déclenchés par une pull request venant d'un fork. Dans les commandes des sections précédentes, remplacez désormais `admin:admin` par `"admin:$GF_PASS"`. Si vous supprimez le secret, Grafana revient à `admin` au déploiement suivant.

**Résultat attendu** : la première commande affiche `401`, la dernière `200`.
